# v0.1.0 — release notes (draft)

First public release. Draft for the maintainer creating the tag; not itself a release.

---

## What this is

An **assessment-coverage and verification layer**. It runs the security engines you already
trust, refuses to overstate what they found, and produces a defensible account of what was
tested, what was blocked, what was never attempted, and why.

Most scanners answer *"what did you find?"*. This answers *"what did you not test?"* — and
on real applications the answer is usually "most of it", which is the point.

## Why you might want it

A scan that exercised a tenth of an application's surface and found nothing is not a clean
result. Nothing in a typical scanner's output says which tenth. This produces a per-operation
ledger where every entry is `executed`, `blocked` or `untested` with a machine-readable
cause, so "no findings" can be read correctly.

Measured on a real application during validation: **84 operations, 10 executed** — with a
stated reason for each of the other 74.

## Highlights

- **Coverage ledger.** Every operation accounted for, every gap attributed to a cause
  (`missing_resource`, `safety_policy`, `no_oracle`, `engine_unavailable`,
  `not_in_specification`, …).
- **Engine orchestration without promotion.** Nuclei, ZAP and a source analyser run under
  supervision — explicit argument vectors and never a shell, an environment built from
  nothing so your credentials cannot reach a third-party process, process groups so a
  killed engine cannot orphan a JVM. Every engine result enters as `observed` with AppSec
  severity `unassessed`, which has no rank and cannot fail a build.
- **A failed engine is never a clean result.** Missing, crashed, hung or timed-out becomes
  a blocked ledger row naming the classes left unassessed.
- **Two native checks.** Declared authentication with an authenticated control request
  behind it, and cross-owner resource access (BOLA) with mutation confirmed only by
  observing state — not by a status code.
- **Framework adapters** (Laravel, NestJS) derive expectations from the application's own
  routing metadata by static inspection. They never execute your code.
- **Surface beyond the specification.** `Link` headers, `robots.txt`, same-origin
  JavaScript literals and five standardised metadata documents. It is not a crawler: one
  page and the scripts it names, and nothing discovered is ever fetched.
- **Scope is the authorization boundary.** Checked before DNS and again on every resolved
  address; cloud-metadata ranges always denied; redirects never followed automatically.
- **Secrets redacted at capture time**, so they are not written and then cleaned.

## External engines — exact validation status

There are three integrations. The source-analysis one accepts two binaries and only one has
been executed.

| Integration | Binary | Status | Version exercised |
|---|---|---|---|
| Nuclei | `nuclei` | real binary validated | v3.11.1 |
| ZAP | `zap.sh` | real binary validated | 2.17.0 |
| Source analysis | `opengrep` | real binary validated | v1.29.0 |
| Source analysis | `semgrep` | **integration support only — never executed** | none |

"Real binary validated" means an automated test ran that binary and asserted the result.
No compatibility is claimed for other versions. All engines are **disabled by default** and
nothing is ever downloaded or installed for you.

## Current limitations

Stated plainly, because the tool's whole argument is that unstated limits are how reports
mislead.

- **No detection-quality measurement.** Precision and recall have never been measured
  against a corpus of real applications. No such claim is made.
- **Authorization coverage is narrow.** One cross-owner boundary per configured fixture
  pair. No roles, no permissions, no function-level authorization, no tenancy.
- **No workflow or business-logic testing.**
- **Resource fixtures are manual.** Identifiers are supplied by hand and go stale when the
  target's data is reset. Measured setup cost for cross-owner testing on a real
  application: 33 configuration lines and six manual steps.
- **Adapters are static and cover two frameworks.** They report what the source says, not
  what runs, and they say what they could not determine.
- **Discovery finds some undocumented surface, never all of it.** No completeness figure is
  offered, because there is no denominator for one.
- **Semgrep is untested code** — see the table above.
- **Not a replacement** for ZAP, Nuclei, Semgrep/opengrep, or for professional testing. It
  coordinates and accounts for them.

## Maturity

`v0.x`. Output schemas (`appsec.report/v1alpha1`, `appsec.run/v1alpha1`, `appsec/v1alpha1`)
may change before 1.0; each is versioned so a consumer can detect a change rather than
misparse it. Pre-1.0, only the latest release is supported.

## Safety

Assess only what you own or are explicitly authorized in writing to test. Prefer local or
staging targets. The URL you pass is the authorization you grant: AppSec contacts that
origin and nothing else unless you widen the scope deliberately. State-changing checks
require the `intrusive` profile and an explicit opt-in. Use dedicated test credentials.

## Install

```bash
go install github.com/jaylordibe/application-security-framework/cmd/appsec@v0.1.0
appsec version
```

Requires Go 1.27+. Built and tested by CI on Linux, macOS and Windows; the
reference-application and real-engine validation runs on Linux.

## First run

```bash
appsec scan http://localhost:3000 --spec-url http://localhost:3000/openapi.json
```

## Verifying the project's own claims

```bash
make check                                   # everything CI runs
go test ./evals/                             # 83 paired evaluation scenarios
APPSEC_REFERENCE_TARGET=http://localhost:8000 \
APPSEC_REFERENCE_SPEC=http://localhost:8000/docs/api.json \
  go test -v -run TestReferenceApplication ./evals/
```
