# Discovery against the reference applications

What M5 actually finds on the two public reference applications, what it does
not, and what could not be established at all.

The short answer, stated first because it is the interesting one: **the four
runtime discovery sources find nothing additional on either application**, and
that is a correct result rather than a failure. The value on these two comes
entirely from the adapter route, and the fixture application is where the runtime
sources are demonstrated.

| | `jaylordibe/laravel-api` | `jaylordibe/nestjs-api` |
|---|---|---|
| Commit read | `8302196` | `84e19a2` |
| Modified | no | no |
| `robots.txt` present | yes — `public/robots.txt` | no |
| `robots.txt` names any path | **no** — see below | n/a |
| JavaScript served from the app's own origin | none committed | none |
| HTML with `<script src>` | `welcome.blade.php`, no script tags | none |
| `.well-known/` documents | none | none |
| Operations the adapter knows | **40** | **84** |

## Why the runtime sources find nothing here

**`laravel-api` ships the Laravel default `robots.txt`:**

```
User-agent: *
Disallow:
```

`Disallow:` with an empty value means "nothing is disallowed". It names no path,
and the parser correctly extracts none — a directive with no value is not a
discovery. A naive implementation would have recorded `/` or an empty string, and
the ledger would have gained a row for a path that does not exist.

**Neither application serves same-origin JavaScript.** `laravel-api`'s `public/`
directory contains `css`, `favicon.ico`, `index.php` and `robots.txt` — Vite build
output is not committed, which is normal and correct. `nestjs-api` is a pure API
with `setGlobalPrefix('api')` and no static assets at all. There is no bundle to
read, so there is nothing to extract.

**Neither publishes `.well-known` metadata.** No OIDC discovery document, no
OAuth authorization-server metadata, no app-site-association file.

**Link headers could not be evaluated.** Both applications must be running to
serve a header, and standing either up requires `composer install` or
`npm install` — which is dependency installation, which is code execution, and
which §33 of the milestone brief and ADR-0014 both forbid this tool from doing.
So this is genuinely **unknown** rather than empty: `laravel-api` may or may not
emit `Link` headers at runtime, and this evaluation cannot say.

That is four sources: three established as empty by reading the repositories, one
that could not be evaluated at all. None of them was faked into producing a
result.

## What M5 does add here

Both adapters know routes a specification is unlikely to document:

- The Laravel adapter reports **40 distinct operations**, including `GET /`
  — the framework's welcome route, which no API specification generated by
  Scramble would contain.
- The NestJS adapter reports **84 distinct operations**, including nested
  resources such as
  `DELETE /api/businesses/{businessId}/memberships/{membershipId}` and
  operational routes such as `DELETE /api/queues/{queue}/jobs/{jobId}`.

Before M5 those were recorded in `adapterUnmatched` and deliberately excluded
from the assessed surface, with the code saying in as many words that testing
them belonged to a later milestone with its own safety questions. This is that
milestone, and the questions have answers: the method comes from the routing
table, the authentication expectation comes from the adapter, and scope is
unchanged. So an adapter-reported route the specification omits is now assessed,
under `discovery.surface.assessAdapterDiscovered`.

**How many of the 40 and 84 are actually "beyond the specification" depends on
the specification the operator supplies**, and that is not a number this document
can state without running both applications. What can be stated is the mechanism:
whatever the specification omits and the adapter knows is now assessed rather
than dropped.

## Where the runtime sources were demonstrated

On a purpose-built fixture application, because the reference applications cannot
demonstrate them. One route reachable through each source, none in the
specification:

```
declared operations:  2
discovered paths:     9 (untested: no method, no stated expectation)
off-origin refs:      2 (recorded, not contacted)
executed: 1  blocked: 0  untested: 10
```

| Discovered path | Provenance |
|---|---|
| `/api/link-only` | `Link` header on the root response |
| `/api/robots-only`, `/admin` | `robots.txt` |
| `/api/js-only`, `/api/admin/users`, `/api/session` | a same-origin bundle |
| `/api/wellknown-only`, `/oauth/authorize`, `/oauth/token` | `/.well-known/openid-configuration` |

And the three results that matter more than the nine paths:

- `GET /api/orders` was named by the specification, a `Link` header **and** the
  bundle. It is **one** operation with three sources — not three surface items.
- The bundle contained `/api/users/42`. That corroborated the documented
  `GET /api/users/{id}` rather than being reported as an undocumented route. A
  literal template match would have filled the undocumented list with every
  identifier the application happens to embed.
- `/admin` was found and is recorded as `untested / not_in_specification`. Its
  ledger row does not say it is sensitive, admin-only or exposed, because
  `robots.txt` said none of those things — it said `Disallow`.

The bundle also contained `fetch("/api/session?token=SECRET-…")`. The path was
discovered; the token appears in **zero** of the nine files under `.appsec/`,
because the query string is dropped at normalization rather than filtered
afterwards.

Two off-origin references — a CDN script and a `preconnect` link — were recorded
and never contacted. Discovery made **8 requests totalling 898 bytes** for the
entire pass.

## What remains impossible to know

- **Whether either application exposes routes nobody references.** A route
  mentioned in no page, no bundle, no header and no metadata document is not
  discoverable by any of these means, and no number here bounds how many those
  are. This is why no report offers a completeness percentage.
- **What HTTP methods the nine discovered paths answer.** Establishing that would
  mean requesting them with guessed methods.
- **Whether any of them should require authentication.** Nothing in a `Link`
  header, a `robots.txt` line or a bundle says so.
- **Whether the reference applications' running behaviour differs from their
  source.** Both evaluations here are reads of a checkout.

## Reproducing this

```
go test ./internal/discovery/     # parsers, budgets, origin rules, adversarial input
go test ./evals/ -run Discovery   # the fixture application, end to end
```

The reference-application figures come from running the two adapters against
fresh clones with no install step:

```
appsec-adapter-laravel --source-root <checkout>
appsec-adapter-nestjs  --source-root <checkout>
```
